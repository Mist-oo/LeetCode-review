# 第三版开发计划与提交约定

建立日期：2026-10-30。状态：开发中，进度见下表及逐功能验收记录。需求依据：[第三版需求](v3-requirements.md)。

## 1. 后续每个小功能的交付方式

继续直接在 `main` 开发，不增加分支/PR 流程，不创建后台自动提交任务。

每完成一个可独立验证的小功能或修复：

1. 检查差异，运行与改动相称的测试或浏览器验收；不得把尚未验证的行为记为完成。
2. 更新 `docs/dev-log.md`，写清实现内容、关键决定、验证结果和遗留问题。
3. 为该功能建立或更新对应的 `docs/verification/v3-<编号>-<功能名>.md` 验收记录；文件在实际开发时创建，本次不预填通过结果。
4. 按需要更新需求状态、设计决策、使用说明和第三方许可。代码、必要文档与验证记录放在同一提交中。
5. 使用 `feat:`、`fix:`、`test:`、`docs:`、`chore:` 提交并推送 GitHub；检查本地与远程状态。

验收记录至少包含：对应需求、实际改动、验证方法及结果、已知限制与剩余工作。日志不写同次提交自身哈希，通过 Git 历史关联。推送成功后才报告已推送；失败保留本地提交、记录实际状态后补推，不强制覆盖远程历史。

## 3. 验证原则

- 文档基线只检查一致性、链接、待办状态和 Git 差异，不为纯文档改动重跑判题性能测试。
- 编辑器改动以实际浏览器交互和必要回归为主；可逆的外观调整不添加只重复实现的测试。
- 固定题面进行逐题语义审核和可执行的覆盖/示例检查；题面改写不能修改原判题规则来迁就内容错误。
- AI 验证默认使用测试服务或可控响应覆盖成功/失败路径；真实服务调用使用用户已配置的服务，不能将模拟测试写成真实接口验收。
- 触控板手势需要在真实设备上检查。环境无法核验时如实记为待验证，不以合成事件冒充实测。
- 最终复用现有存储、HTTP、判题等与变更相关的回归；修改协议、参考答案或测试集时才重新扩大题库审计范围。
- 个人数据库、配置密钥、生成缓存和验收临时文件不提交。启动升级前后检查原始数据保留，正式库不写入测试记录。
